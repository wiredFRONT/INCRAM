# No host renders all of MCPL

State of the world: 12 November 2026. Labels used throughout, matching the umbrella report: **[P]** = read from the owner's own spec, repo or documentation page on that date; **[U]** = the researchers marked it UNVERIFIED (reason given where known); **[S]** = secondary source only (tracker, blog, press, mirror); **[I]** = inference by a researcher or by this synthesis, not a sourced fact. Evidence items in section 4 also carry **[PR]** peer-reviewed, **[PP]** preprint, **[VR]** vendor-reported. One method caveat applies to every [P]: the researchers read pages through a fetch-and-summarise tool, so short quoted strings should be spot-checked against the page before they are reproduced as normative text, and everything said about the two MCP Apps spec files outside quotation marks is a summary.

An MCP server can drive exactly two interaction surfaces that hosts already implement, MCP elicitation and MCP Apps, and no host surveyed documents both in a usable state: the Claude consumer apps render Apps but have no elicitation, Claude Code has elicitation in both modes but does not render Apps, ChatGPT documents Apps and is silent on elicitation, and the vibe-coding platforms (Lovable, Bolt, Replit, v0, Base44) document tools only. The floor MCPL can promise on day one is therefore narrow: a remote Streamable HTTP server, OAuth or no auth, tools carrying `readOnlyHint`, guidance delivered through tool descriptions and tool results, and the host's own approval card as the only guaranteed human checkpoint. Everything friendlier is a runtime route chosen per request from declared capabilities, never from the host's name. Three planning items need correcting: an in-chat "accept" is asserted by the client and is not proof of a human click (only a page MCPL serves gives that); under MCP 2026-07-28 a server cannot open a prompt on its own, so "signal-triggered" means attaching a question to a call the model already made; and Open-JSON-UI has no primary source at all. Four parts of the design have no upstream to align to and are MCPL's to define: workflows and chained events, signed signal provenance, anti-nag policy, and provable approval. The published evidence backs a small always-loaded surface with on-demand loading and a small fine-tuned classifier, and it backs passive UI; it does not back a calendar normalization cadence, unattended long-horizon user modelling by a small model, inference of "desire to learn", or learning from explanation the user does not work with.

### Elicitation changed its wire format twice in twelve months

The input vocabulary is stable and small. Form mode accepts a flat object of string, number, integer, boolean and enum properties; since 2025-11-25 enums come in four shapes (single or multi-select, titled or untitled, using `oneOf` / `anyOf` with `const` and `title`), and every primitive takes a `default` **[P]** ([2026-07-28 elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation), [2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)). The 2025-06-18 revision had only single-select `enum` with a parallel `enumNames` array **[P]** ([2025-06-18 elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)). Nested objects, arrays of objects, widget hints, sliders, images and file inputs do not exist; file input is an open draft proposal, SEP-2356 **[P]** ([File Uploads WG](https://modelcontextprotocol.io/community/working-groups/file-uploads)). So **a multiple-choice question with friendly labels and a default is a first-class form-mode construct, and a thumbs or slider control is not**: the value travels, the widget is whatever the host draws.

The delivery mechanism is the unstable part. Through 2025-11-25 the server sent `elicitation/create` as its own request. In 2026-07-28 that pattern is gone: the server answers `tools/call`, `prompts/get` or `resources/read` with an `InputRequiredResult` holding `inputRequests` and an opaque `requestState`, and the client retries the original request with `inputResponses` under a new JSON-RPC id **[P]** ([MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)). The spec tells servers to treat `requestState` as attacker-controlled and to protect its integrity (HMAC or AEAD) wherever it affects authorization or business logic **[P]** (same page). The URL-mode completion notification and `elicitationId`, added in 2025-11-25, were removed eight months later; the client now learns the outcome by retrying, and the server "may need to block" on that retry **[P]** ([2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Released 2026-07-28 also dropped `_meta` from elicitation requests and results by accident; the draft restores it **[P]** ([draft changelog](https://modelcontextprotocol.io/specification/draft/changelog)). The researcher's reading is that a server covering all three revisions needs three code paths **[I]**. Whether error `-32042` was formally removed is **[U]** (absent from the 2026-07-28 page, not listed in the changelog), and whether `pattern` on strings survives is **[U]** pending a read of `schema.ts`.

The sensitive-data rule is firm and has a definition. Since 2025-11-25 servers must not use form mode for passwords, API keys, access tokens or payment credentials and must use URL mode for them; "sensitive" means secrets and credentials that grant access or authorize transactions, and name, email address and username are expressly not categorically prohibited **[P]** ([2026-07-28 elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). URL-mode data other than the URL itself is not exposed to the client, the server must verify who opens the URL, the URL must not carry PII or be pre-authenticated, and servers "MUST NOT rely on URL mode elicitation to authorize users for themselves" **[P]** (same page). One-time codes, magic links and email verification are not named anywhere; classing an OTP as sensitive is the researcher's conservative reading **[I]**.

Two absences matter for a passive design. The line telling clients to rate-limit elicitation, present in 2025-06-18 and 2025-11-25, is missing from the 2026-07-28 page and the changelog does not mention it; whether that was deliberate is unknown **[P for the absence]**. And MRTR explicitly lets a server prompt repeatedly on the same request **[P]** ([MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)). No spec read contains a cooldown, a cap or a "do not re-ask" rule.

### MCP Apps is the only rich surface, and its consent hooks are optional

A tool points at a `ui://` resource with MIME type `text/html;profile=mcp-app`; the host renders it in a sandboxed iframe and enforces a CSP built from the resource's declared domains, with deny-all as the default **[P]** ([stable spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [draft](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx)). Inside the view any HTML works, so sliders, thumbs and multi-step forms are author-defined. What the user did returns by one of three paths: the view calls a server tool (including tools visible only to the app), it overwrites model context with `ui/update-model-context`, or it posts a conversation message with `ui/message` **[P]** (stable spec). There is no accept / decline / cancel triad and no method for reading conversation history **[P]**.

Three properties bound how far MCPL can lean on it. First, consent is permissive: hosts "MAY" ask before `ui/message` and "MAY" gate proxied calls, where elicitation's client duties are "MUST" since 2025-11-25 **[P]**. Second, the fetched text surfaced no rule on collecting credentials inside a view; that absence is **[U]** against the full spec. Third, the stable spec describes capability negotiation inside `initialize`, which core 2026-07-28 removed; the working group lists protocol alignment as in progress, so how a 2026-07-28 client advertises the extension is unconfirmed and a server should detect both **[P for the mismatch, I for the advice]** ([Apps WG](https://modelcontextprotocol.io/community/working-groups/apps)). Draft-only features (`ui/download-file`, app-provided tools, sampling from the view) must be feature-detected through `hostCapabilities` **[I]**.

### The Apps SDK folded into MCP Apps; Open-JSON-UI cannot be found

ChatGPT documents that it implements the open MCP Apps standard and keeps `window.openai` as an alias layer with ChatGPT-only extras (checkout, file helpers, modal, widget state); OpenAI's own advice is to use the standard bridge, feature-detect extensions, and never branch on host name **[P]** ([MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt)). The compatibility date of 2026-02-22 comes from the plugin changelog **[P]** ([changelog](https://developers.openai.com/plugins/changelog)). For crosswalk purposes the Apps SDK is "MCP Apps plus proprietary extensions" **[I]**. MCP-UI likewise continues as an SDK that implements MCP Apps **[P]** ([launch post](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)).

Open-JSON-UI has no locatable primary source. AG-UI's docs describe it as an open standardization of OpenAI's internal schema without linking a spec; a CopilotKit showcase page shows an example wrapper; the main CopilotKit URLs titled open-json-ui now serve A2UI content; OpenAI's UI docs do not mention it **[P]** ([AG-UI generative UI specs](https://docs.ag-ui.com/concepts/generative-ui-specs), [CopilotKit showcase](https://docs.showcase.copilotkit.ai/langroid/generative-ui/open-json-ui)). The researcher treats it as a CopilotKit-side label, not an alignable spec **[I]**.

AG-UI models a question as a run that ends with `outcome = interrupt` and a later run carrying `resume[]`; its `responseSchema` is unrestricted JSON Schema, and it has no URL mode and no out-of-band secret channel **[P]** ([interrupts](https://docs.ag-ui.com/concepts/interrupts)). Its own pages disagree on whether `outcome` shipped in 1.0: the events page flags it as draft, the changelog lists it as shipped **[P]** ([events](https://docs.ag-ui.com/concepts/events), [changelog](https://docs.ag-ui.com/spec/draft/changelog.md)). Capability discovery is one-way from agent to client, which is why a server-side-only MCPL cannot reach it **[P, I]** ([capabilities](https://docs.ag-ui.com/concepts/capabilities)).

A2UI's basic catalog has what MCPL's interaction set needs as vocabulary: `ChoicePicker` (single or multi-select), `Slider`, `TextField`, `CheckBox`, `Button`; thumbs and link-out are compositions, not components **[P]** ([basic catalog guide](https://a2ui.org/specification/v1.0-basic-catalog-implementation-guide/)). It has no provenance or trust fields and no secret channel beyond an in-band `obscured` text variant **[P]** ([v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/)). Version status is contested between its own sources: the site calls v1.0 current (last updated 2026-06-08) while the repo README calls v0.9.1 production and v1.0 a release candidate **[P]** ([v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/), [README](https://raw.githubusercontent.com/a2ui-project/a2ui/main/README.md)). Two researchers also differ on the A2A carriage: one, working from background knowledge, recorded MIME `application/json+a2ui` for v0.8 as **[U]**; the other read the v1.0 extension spec and found `application/a2ui+json` and extension URI `https://a2ui.org/a2a-extension/a2ui/v1.0` **[P]** ([A2UI A2A extension](https://a2ui.org/specification/v1.0-a2ui-extension-specification/)). That page names the activation header `X-A2A-Extensions`; the A2A 1.0 spec names it `A2A-Extensions`. Unresolved.

### WebMCP is a Chromium-family draft; MCP core went stateless; A2A is not needed

WebMCP is in origin trial in Chrome 149+ and Edge 150+; WebKit states opposition and a Mozilla participant proposed neutral, with final labels not visible on either thread **[P]** ([implementation status](https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md), [WebKit #670](https://github.com/WebKit/standards-positions/issues/670), [Mozilla #1412](https://github.com/mozilla/standards-positions/issues/1412)). The current IDL exposes `document.modelContext` with `registerTool`, `getTools` and `executeTool`; `provideContext`, `clearContext` and `unregisterTool` are gone **[P]** ([WebMCP spec](https://webmachinelearning.github.io/webmcp/)). The declarative attributes are unhyphenated (`toolname`, `tooldescription`, `toolparamdescription`, `toolautosubmit`) and live only in an explainer whose form-to-schema algorithm is marked TBD **[P]** ([declarative explainer](https://github.com/webmachinelearning/webmcp/blob/main/declarative-api-explainer.md)). The explainer and the spec disagree on the cancel event name (`toolcanceled` against `ontoolcancel`). Chrome's own declarative page could not be fetched, so Chrome's spelling is **[U]**. Its tool shape (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`) is nearly field-for-field the MCP tool definition **[P]**, and it adds two hints, `consequentialHint` and `untrustedContentHint`; whether MCP 2026-07-28 has an equivalent of the second is **[U]** because the annotation list was not re-read.

MCP core 2026-07-28 removed sessions and the handshake: each request carries protocol version and client capabilities in `_meta`, servers must implement `server/discover`, every result carries `resultType`, list results need `ttlMs` and `cacheScope`, cross-call state moves to explicit server-minted handles, and Roots, Sampling and Logging are deprecated with a twelve-month minimum window **[P]** ([Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Client ID Metadata Documents are preferred over Dynamic Client Registration, and authorization stays optional **[P]** ([Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). SEP-3398, accepted 2026-10-14, sets six-monthly releases and moves the next one from December 2026 to 30 March 2027 **[P]** ([SEP-3398](https://modelcontextprotocol.io/seps/3398-release-cycle-updates)). Identity fields are unsigned, server `name` should not be used for disambiguation, and clients must treat tool annotations as untrusted unless the server is trusted **[P]** ([Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). Serving public tools unauthenticated and challenging per operation with 401 / 403 is possible by composition; the spec text read does not describe that mixed mode explicitly **[I]**. The status of the server `instructions` field after the removal of `InitializeResult`, and the `server/discover` result shape, were not retrieved **[U]**.

A2A's constructs presuppose two independently operated agents; the researcher's judgment is that it is not relevant to one user attaching one server to one host **[I]**. It contributes the only cryptographic element found in any of these specs: optional JWS signatures over a JCS-canonicalised Agent Card **[P]** ([A2A specification](https://a2a-protocol.org/latest/specification/)). The spec site lists 1.0.0 as latest while the changelog has 1.0.1 **[P]** ([CHANGELOG](https://github.com/a2aproject/A2A/blob/main/CHANGELOG.md)). The last third of the spec was not read.

### Context, discovery and packaging formats

AGENTS.md has no required fields and no size limit of its own; every real limit is the host's. Codex caps the combined files at 32 KiB by default, Lovable caps instructions at 10,000 characters, and Claude Code advises under 200 lines **[P]** ([Codex guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Lovable](https://docs.lovable.dev/features/knowledge), [Claude Code memory](https://code.claude.com/docs/en/memory)). Claude Code's docs say it reads CLAUDE.md, not AGENTS.md, and recommend an `@AGENTS.md` import or a symlink; Gemini CLI reads it only when added to `context.fileName` **[P]** ([Gemini CLI](https://geminicli.com/docs/cli/gemini-md/)). The adoption figure on the site, "over 60k" projects, is the same one used in December 2025 **[P]** ([agents.md](https://agents.md)).

Agent Skills requires only `name` (64 characters, lowercase and hyphens, matching the folder) and `description` (1,024 characters), and budgets about 100 tokens of metadata per skill, under 5,000 tokens and 500 lines for the body **[P]** ([specification](https://agentskills.io/specification)). Hosts truncate further: Claude Code cuts the listing text at 1,536 characters, Codex gives the whole skills list 2% of the context window or 8,000 characters **[P]** ([Claude Code skills](https://code.claude.com/docs/en/skills), [OpenAI build-skills](https://learn.chatgpt.com/docs/build-skills)). Uploads to claude.ai and the Skills API accept only the six standard fields and hard-fail on others, so a portable skill ships those six and nothing else **[P, I]**. The supply chain is unvetted: Snyk scanned 3,984 skills and found 36.82% with at least one flaw and 76 confirmed malicious **[VR, measured]** ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)). The two researchers got different results on the client list: one read the showcase data file and counted 46 clients including Cursor, VS Code, Gemini CLI and Goose; the other found the showcase rendered client-side, got no names, and so marks skills support in VS Code, Cursor, Gemini CLI, goose and Kiro as **[U]**. Listing by the format's own site is not host documentation either way.

llms.txt is a publishing convention. Ahrefs found 97% of published files received zero requests in May 2026, with coding agents the largest AI consumers; Common Crawl found about 68% of files templated by site builders; `llms-full.txt` is not part of the proposal **[measured, published by the companies that ran the analyses; P for the proposal text]** ([Ahrefs](https://ahrefs.com/blog/llmstxt-study/), [Common Crawl](https://commoncrawl.org/blog/a-content-analysis-of-llms-txt-files-from-the-july-2026-crawl-archive), [llmstxt.org](https://llmstxt.org)).

The MCP Registry verifies a reverse-DNS namespace (GitHub account, or a domain by DNS TXT or a well-known HTTPS file) but not remote URLs, hosts metadata only, and limits `description` to 100 characters **[P]** ([authentication](https://modelcontextprotocol.io/registry/authentication), [quickstart](https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/modelcontextprotocol-io/quickstart.mdx)). A sub-registry is any service re-serving the same API with its own data under a namespaced `_meta` key, and Lovable lets a workspace admin paste in such a registry URL **[P]** ([aggregators](https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/modelcontextprotocol-io/registry-aggregators.mdx), [Lovable registries](https://docs.lovable.dev/integrations/mcp-registries.md)). Lovable's example path is `/v0/servers` while the official API is `/v0.1/`; which versions Lovable accepts needs a live test. Nothing in `server.json` advertises MCP Apps or other extensions **[P for the absence in the reference read]**.

On packaging, Agent Plugins 1.0.0 standardises only skills plus `mcp.json`; Codex, Cursor and VS Code each also accept Claude-format plugins **[P]** ([agent-plugins.org](https://agent-plugins.org), [Codex](https://developers.openai.com/codex/plugins/build), [Cursor](https://cursor.com/docs/plugins/building), [VS Code](https://code.visualstudio.com/docs/copilot/customization/agent-plugins)). A `CLAUDE.md` at a Claude Code plugin root is not loaded, so always-on instructions cannot ship in that bundle **[P]** ([plugins reference](https://code.claude.com/docs/en/plugins-reference)). Rendering UI is not a capability of any bundle format read; where UI exists it hangs off the MCP server **[I]**. Anthropic is not among the Agent Plugins maintainers, and whether Claude Code reads the root `plugin.json` is undocumented.

Three points of researcher disagreement sit behind the table and are left open. On route order for interactive prompts, the declarative-UI researcher puts form elicitation first, URL mode second and Apps third; the host researcher puts an App first where negotiated, then elicitation, then text; the elicitation researcher routes per need (elicitation for choices, Apps for feedback and passive UI). **The lowest common denominator**, taking ChatGPT, the Claude apps, Cursor, VS Code Copilot and Claude Code as the top five (an assumption; no usage ranking was sourced), is a remote Streamable HTTP server with OAuth or no auth, tools annotated `readOnlyHint`, and the host's per-call approval prompt **[P per host, I for the set]**. Elicitation, Apps, prompts, resources and instruction injection each fail or go undocumented in at least one of the five. What MCPL can promise everywhere on day one is behaviour delivered through tool descriptions and tool results **[I]**. Adding Gemini weakens the floor further: consumer Gemini custom MCP is **[U]** and Gemini CLI documents neither elicitation nor Apps. Covering Anthropic's own surfaces alone needs both paths, an App for the consumer apps and elicitation for Claude Code **[I]**.

Four operational consequences follow from host documentation. A declared capability does not guarantee a rendered dialog: Claude Code declares a different `elicitation` shape depending on connection type and version, so the branch must be on the declared shape per request **[P, I]**. Issue titles on a third-party mirror report Claude Code surfaces declaring the capability and then auto-declining or auto-cancelling; the bodies were not read and this is a lead only **[S]** ([issue index](https://claudeissues.com/issue/79174-mcp-elicitation-capability-is-declared-but-requests-are-auto-declined-print-mode)). Hiding write tools when elicitation is missing leaves users with a silently read-only connector, as one server author reported in the claude.ai thread; degrade to text instead **[S, I]**. And a portable widget is inline, self-contained HTML with no external origins, at most two actions, reporting through `tools/call`, because VS Code fills the chat box without sending on `ui/message` and Claude blocks all external origins by default **[P, I]** ([Claude design guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines)).

On local models the evidence is thin. LM Studio, Jan, Open WebUI, goose, Msty and AnythingLLM are MCP hosts; LM Studio and Open WebUI both warn that tool-heavy servers overflow or degrade local models **[P]**. The one quantitative source is a general tool-selection benchmark from June 2025 (Qwen3 14B 0.971 F1, Qwen3 8B 0.919, Gemma3 4B 0.733, against GPT-4 at 0.974, with 84 to 142 seconds per interaction on an M4 Max) **[S, measured, not MCP-specific]** ([Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)). No MCP-specific benchmark for 4B to 14B models was found.

No maintained official matrix exists to lean on. The old per-feature client table is no longer served; the remaining official page is a community-maintained Extension Support Matrix covering extensions only, already out of step with host docs, and its cell values did not survive text extraction **[P]** ([Extension Support Matrix](https://modelcontextprotocol.io/extensions/client-matrix)). Third-party trackers contradict themselves and each other **[S]**. MCPL has to own a tested table.

## What the evidence supports and where it stops

### Context rot is real; a calendar cleanup cadence is unmeasured

Degradation with input length is among the best-replicated results in the literature. NoLiMa found 11 of 13 long-context models at or below half their short-context score by 32K tokens **[PR]** ([arXiv 2502.05167](https://arxiv.org/html/2502.05167v3)); Lost in the Middle found position effects **[PR]** ([arXiv 2307.03172](https://arxiv.org/abs/2307.03172)); Chroma's 18-model report found every model did better on roughly 300-token focused prompts than on roughly 113k-token full ones **[VR, not peer-reviewed]** ([Chroma](https://www.trychroma.com/research/context-rot)). Chroma's own limitations say it does not separate length from task difficulty, and press coverage noted the company sells a vector database **[S]** ([The Decoder](https://the-decoder.com/yet-another-study-finds-that-overloading-llms-with-information-leads-to-worse-results/)). Chroma also reports no notable needle-position effect, which sits awkwardly beside Lost in the Middle; the notes do not reconcile the two.

Whether the effect is shrinking is contested. A 2026 single-author preprint reports 100% single-needle retrieval at 1M tokens for three flagships, with multi-hop traversal still degrading **[PP, abstract only]** ([arXiv 2605.02173](https://arxiv.org/abs/2605.02173)). A second 2026 preprint finds monitors miss a dangerous action after about 800K benign tokens 2 to 30 times more often **[PP, abstract only]** ([arXiv 2605.12366](https://arxiv.org/abs/2605.12366)). Claude Code's best-practices page now lists aggressive context-window management as outdated advice given 1M-token windows with automatic compaction **[P, vendor guidance]** ([best practices](https://code.claude.com/docs/en/best-practices)). The honest reading is that simple retrieval has largely stopped degrading at practical lengths while reasoning over long context has not, so MCPL's guidance is better framed around relevance, cost and adherence than around running out of space **[I]**.

For the audience, the multi-turn result matters more than the length result. Laban and colleagues measured an average 39% drop from fully specified single-turn tasks to underspecified multi-turn ones across 15 models, visible after two turns, with restatement recovering only part **[PP; later venue U]** ([arXiv 2505.06120](https://arxiv.org/html/2505.06120v1)). A non-expert drip-feeding requirements is that condition, and shortening context does not address it **[I]**. The study used LLM-simulated users.

Mitigations matching MCPL's plan have numbers, nearly all vendor self-reports on undisclosed internal evals: deferred tool loading cut context about 85% and raised accuracy on an internal MCP eval from 49% to 74% for one model **[VR]** ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)); context editing plus a memory tool improved an internal agentic-search eval 39% **[VR]** ([Anthropic](https://claude.com/resources/articles/context-management)). On description length, a preprint covering 856 tools found richer descriptions raise success by a median 5.85 points while adding 67% more steps, and that compact, purpose-clear variants often hold reliability **[PP, abstract only]** ([arXiv 2602.14878](https://arxiv.org/abs/2602.14878)). Too terse is its own failure mode.

On always-loaded files the controlled evidence cuts against volume. ETH Zurich's study found no significant change in task success from either generated or developer-written context files, about 20% higher cost, and developer-written files beating generated ones by about 7 points (p = 0.038) **[PP, v3]** ([arXiv 2602.11988](https://arxiv.org/html/2602.11988)). A separate study associates AGENTS.md with 28.64% lower median runtime and 16.58% fewer output tokens across 124 pull requests **[PP, association]** ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404)). These pull in different directions on cost; they measure different things with different designs, and both stand. ETH also shows agents obey what the file says, which is what makes a stale line harmful. Whether ETH's first version reported reduced success, as March 2026 secondary coverage says, is **[U]**; its "at most 19%" cost figure needs checking against the PDF.

Not supported: any calendar cadence. No authoritative source prescribes a review interval for context files; published mitigations act per session, and vendor guidance is trigger-based (add a line after a repeated mistake, delete what the code shows) **[P for the guidance, I for the gap]**. Retrieval against long context is itself contested in peer-reviewed work, with two studies finding long context generally ahead when resources allow **[PR, PP]** ([arXiv 2407.16833](https://arxiv.org/abs/2407.16833), [arXiv 2501.01880](https://arxiv.org/abs/2501.01880)). "Structure prevents context rot" overstates the evidence; "reduces exposure to it" is defensible **[I]**.

### A small classifier is supported; a small unattended user-modeller is not

The headline NVIDIA paper is a position paper with no original experiments; its replaceability estimates come without a measurement method **[PP]** ([arXiv 2506.02153](https://arxiv.org/pdf/2506.02153)). The strongest empirical result, Orchestrator-8B, is the reverse of MCPL's topology: a fine-tuned 8B model drives and calls frontier models as tools, still invoking GPT-5 in about 40% of steps on one benchmark, after reinforcement-learning training on purpose-built data **[PP]** ([arXiv 2511.21689](https://arxiv.org/html/2511.21689v1)). Routing results are real but benchmark-dependent: RouteLLM kept 95% of GPT-4 quality at large savings on one benchmark and still needed 54% GPT-4 calls on another **[PP]** ([LMSYS](https://lmsys.org/blog/2024-07-01-routellm/)).

Narrow classification by a fine-tuned small model is well supported: a 1B model reached 99% on multilingual intent recognition, on synthetic training and test data **[PP]** ([arXiv 2510.21970](https://arxiv.org/abs/2510.21970)). Tracking a user over time is not: on the nearest benchmark, frontier models reach only about 50% at following an evolving profile, and no small-model result on that task was found **[PR]** ([arXiv 2504.14225](https://arxiv.org/abs/2504.14225)). Third-party tool-calling scores for late-2026 small models conflict outright (0.503 on BFCL v4 for one Qwen 4B against "high 80s" claimed for another, the latter admitted to be illustrative); both are **[U]**.

Two architectural facts from the host research bear on this more than the papers do. Sampling, the MCP route by which a server could borrow the host's model, is deprecated in 2026-07-28 and unsupported by Claude's client **[P]**. And an MCP server cannot assume the user has local inference, so where the companion runs is open, with privacy consequences either way **[I]**.

### Coarse skill inference works; "desire to learn" has no validated measure

Estimating expertise from a few turns is feasible at roughly 0.4 to 0.65 mean absolute error on a five-point scale. ProfiLLM's figures are from synthetic users with a five-person human check, and intermediate users were profiled worst **[PP]** ([arXiv 2506.13980](https://arxiv.org/html/2506.13980v1)). ExPerT, with 40 students, reached 0.398 using ten within-user examples and showed expertise-conditioned answers raising satisfaction from 3.71 to 4.36 of 5; it degrades cold-start, which is when MCPL would need it **[PR per anthology listing]** ([arXiv 2607.01242](https://arxiv.org/html/2607.01242)). That paper's arXiv identifier and listed date are inconsistent on the page read. Both it and a large correlational Microsoft study measure satisfaction, not task success or learning **[PR]** ([arXiv 2502.18685](https://arxiv.org/html/2502.18685v1)). No study found infers programming expertise from prompts to coding assistants, and none infers or validates intent to learn.

The risk side is documented. Models given biographies marking a user as less educated answered less accurately and, in one model, condescendingly 43.7% of the time; the models are older and the biographies explicit rather than inferred **[PR, via press summary]** ([MIT News](https://news.mit.edu/index%2ephp/2026/study-ai-chatbots-provide-less-accurate-information-vulnerable-users-0219)). LLMs infer personal attributes from text at up to 85% top-1 accuracy **[PR]** ([arXiv 2310.07298](https://arxiv.org/abs/2310.07298)). In a small study, users shown inferences about themselves reacted more with curiosity than distress, and were uncomfortable when an inference was wrong or used beyond its expected purpose **[PP, abstract only, n = 18]** ([arXiv 2605.10013](https://arxiv.org/abs/2605.10013)). Put together, the lower-risk design is a default that adds explanation without withholding or simplifying content, with the inference shown to the user rather than hidden; "without the user noticing" runs against the one reaction study available **[I]**. Any stored profile is profiling under GDPR Article 4(4) and an inference under the CCPA definition; both statements come from secondary summaries, not the legal texts **[S]**, and this is factual background, not legal advice.

### Learning needs learner effort; explanation alone is not shown to work

The three vendor learning modes are prompt-level behaviours users can switch off **[S]** ([VentureBeat](https://venturebeat.com/ai/anthropic-takes-on-openai-and-google-with-new-claude-ai-features-designed-for-students-and-developers/)). The only outcome data on any of them is OpenAI's own preliminary trial: about 15% higher exam scores in microeconomics, no distinguishable effect in neuroscience **[VR]** ([OpenAI](https://openai.com/index/understanding-ai-and-learning-outcomes/)).

The broader evidence is consistent from both directions. A Harvard crossover trial found an engineered AI tutor more than doubled median learning gains over in-class active learning, with no retention test **[PR]** ([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12179260/)). A study of nearly 1,000 students found plain GPT-4 raised practice grades 48% and left students 17% below never-access peers once removed, a harm largely mitigated in a guard-railed tutor arm **[PR]** ([Stanford SCALE](https://scale.stanford.edu/ai/repository/generative-ai-can-harm-learning)). Anthropic's trial with 52 mostly junior engineers found a 50% quiz score with AI against 67% hand-coding; users who generated code and then asked questions scored 86%, delegators 39%, in a hand-coded, non-causal pattern analysis **[PP, vendor]** ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). The most-cited positive meta-analysis was retracted in 2026 **[S; retraction notice not read]** ([Plagiarism Today](https://www.plagiarismtoday.com/2026/07/15/study-claiming-ai-helps-students-learn-retracted/)). The outcome turns on whether the learner does cognitive work; transparent, unhurried explanation that the user does not engage with resembles delegation **[I]**.

Passive UI is supported and bounded. In one study 53.3% of proactive interventions led to engagement, 34.7% were ignored and 12.1% were disruptive, with task boundaries the best trigger and idle-time triggers misfiring **[PR, n = 18]** ([arXiv 2502.18658](https://arxiv.org/html/2502.18658v4)); in another, proactive suggestions raised tests passed 12 to 18% while only 45% preferred the more frequent variant **[PP]** ([arXiv 2410.04596](https://arxiv.org/html/2410.04596v1)). The expectation that most users consume and a few learn is consistent in direction with a roughly 5% median freemium conversion for developer products and about 47% direct answer-seeking in student conversations, but neither measures deep-learning engagement and no figure for that share was found **[S, VR, I]**.

## What the research corrects in the plan

References are to the decisions-and-opens ledger and the research plan.

**D25 and A7, proof of the approval click.** The ledger lets the AI create the account "once it is proven the user clicked the approval in the chat", and A7 treats in-chat approval as proof on hosts with real elicitation UI. No revision gives protocol-level proof. The result is client-authored JSON; Claude Code documents an `Elicitation` hook that answers without a dialog, and VS Code cancels requests in Autopilot **[P]**. Only a click on a page MCPL serves, with the browser session matched to the MCP subject, is observable by the server. Form accept should be labelled host-attested.

**D17, account creation without a browser.** Name and email in form mode are explicitly allowed; passwords are not; verification has to leave the chat (emailed link) on a conservative reading **[P, I]**. Separately, the spec forbids using URL-mode elicitation to authorize the user to the server itself, so sign-in to MCPL is MCP authorization (OAuth between client and server), and "continue with Google" as sign-up sits on that boundary **[P, I]**. On the Claude consumer apps and, as far as documented, ChatGPT, there is no elicitation at all, so the in-chat step there is an App button or plain text.

**The ledger's "verified fact" on elicitation.** Accept / decline / cancel and URL mode for secrets hold. What the entry omits: delivery changed to MRTR, the completion notification no longer exists, and URL mode is still flagged as subject to change.

**Signal-triggered prompts.** Under 2026-07-28 a prompt can only ride a `tools/call`, `prompts/get` or `resources/read` the model or host already issued **[P]**. "UI appears on a signal, never on a timer" survives only as "the server decides, on a call in flight, whether to attach a question".

**A3, the spec inventory.** Open-JSON-UI is not an alignable spec. The inventory was missing Agent Plugins 1.0.0, the MCP Tasks extension, and MCP-UI as the Apps reference implementation. The Apps SDK is no longer a separate row.

**D16, rich UI delivered as a host plugin.** Plugin bundles carry skills and MCP config; none read carries UI. Rich UI is delivered by the MCP server through MCP Apps; the plugin is how skills and the server definition get installed.

**D8, D22 and "whatever AI they already use".** ChatGPT developer mode excludes the Free plan and Claude Free allows one custom connector **[P]**. On the vibe-coding platforms the server reaches only the build chat. Anonymous-then-upgrade access is achievable by composition but is not a named spec feature **[I]**.

**L4, upkeep cadence, and the research inputs.** No source supplies a cadence. Of the plan's named inputs, Chroma is a vendor report with a stated conflict of interest, the NVIDIA headline is a position paper, ToolOrchestra is the reverse topology, and ProfiLLM's numbers are synthetic.

**WebMCP details.** Anything written against `navigator.modelContext`, `provideContext` or hyphenated `tool-name` attributes is stale relative to the 11 November 2026 draft **[P for the current draft, I for the staleness]**.

**The skill profile.** The plan's constraint that an MCP server sees only what the host sends is confirmed, and tightened: the Apps spec has no method to read conversation history and Sampling is deprecated.

## Conclusion

The research turns MCPL from a single interaction design into a capability ladder with a text floor. The alignment work is small, because for every interaction MCPL wants there is either exactly one upstream (elicitation, Apps, AGENTS.md, Agent Skills, `server.json`, Agent Plugins) or none. The engineering weight sits in the routing and in the four places with no upstream, and those four are where the stigops-AI discipline has something to contribute that the protocol authors have left open: a declared interaction graph, signed signals, a restraint policy, and approval evidence a server can verify.

The least comfortable finding concerns the learning goal. A purely passive design is the one the interruption studies favour and also the one the learning studies say produces the least learning, because the gains appear when the user does the work. That tension is not resolvable from the literature; it is an experiment MCPL will have to run, which fits D26.

## Findings that change the plan

1. Treat in-chat accept as host-attested. Use a page MCPL serves for any approval that must be a human act; relabel D25 and A7 accordingly.
2. Build prompts as attachments to calls already in flight. No server-initiated prompts exist in 2026-07-28.
3. Promise tools-only on day one: remote Streamable HTTP, OAuth (CIMD with DCR fallback) or no auth, `readOnlyHint`, guidance in tool descriptions and results, essentials of server instructions in the first 512 characters.
4. Implement both an MCP App path and an elicitation path; neither alone covers Anthropic's surfaces, and branch on declared capability per request.
5. Build the server dual-era (answer `initialize` and per-request `_meta`), stateless, with integrity-protected `requestState`; do not depend on Sampling, Roots or protocol Logging.
6. Keep secrets, one-time codes and sign-in out of forms; sign-in to MCPL is MCP authorization, not elicitation.
7. Drop Open-JSON-UI; fold the Apps SDK into MCP Apps; add Agent Plugins to the inventory.
8. Rich UI ships from the server, not the plugin; the plugin ships skills and server config.
9. Define MCPL's own constructs for workflows and chained events, signed provenance (borrow the JCS plus JWS recipe), anti-nag policy, and approval evidence.
10. Emit work-list entries in the MCP tool-definition shape; treat WebMCP as an optional, date-pinned web output.
11. State the upkeep cadence as an MCPL default with event triggers ahead of the calendar; no source backs a number.
12. Scope the companion model to narrow classification; do not plan on unattended long-horizon user modelling or on inferring desire to learn.
13. Make any skill inference visible to the user and additive (more explanation, nothing withheld).
14. Own a tested host compatibility table; no official one exists.
